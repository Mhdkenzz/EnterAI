6.2 Migration 0021: provider-owned SCIM mappings
------------------------------------------------

Before: mappings used organization plus SCIM external ID, not a durable owner
provider. Provider A could collide with or potentially mutate provider B identity
records inside the same organization.

After:

- identity_provider_id owns each new mapping.
- Provider foreign key and partial unique index on
  (identity_provider_id, scim_external_id) enforce the boundary.
- Reads/writes/OIDC subject resolution require exact provider ownership.
- New live writes cannot create unowned mappings.

Legacy policy:

- The migration does not guess ownership.
- Ambiguous rows remain NULL/unowned and invisible to every provider.
- Affected identities are deactivated/session-revoked when quarantined.
- Recovery requires an operator to identify and explicitly rebind the correct
  provider out of band.

This operational cost is intentional: silent transfer to an arbitrary provider
would be a cross-tenant disclosure.

6.3 Migration 0022: verified domain ownership
---------------------------------------------

- Added domain_verified_at.
- Canonicalized legacy domain spellings.
- Resolved duplicates fail-closed.
- Added global uniqueness only for active, verified claims.
- Prevented inactive/unverified/expired rows from permanently locking domains.
- Compared index columns, uniqueness, and WHERE predicate, not merely names.
- Added DNS TXT challenge generation/verification and claim expiry/reclaim.
- Added conflict handling for simultaneous claims.

DNS race defense:

The verification write conditionally matches the exact domain that was checked.
If an admin patches domain A to domain B while DNS lookup is in flight, proof for
A cannot be stamped onto B.

6.4 Migration 0023: mapping organization alignment
--------------------------------------------------

Before: mapping.organization_id, user_id, and provider_id were independent. A row
could reference organization A, a user from B, and a provider from C.

After:

- Unique parent keys on (id, organization_id).
- Composite foreign keys align mapping/user and mapping/provider organization.
- Inconsistent historical rows are quarantined, not deleted or guessed.
- Affected users are deactivated and session epochs advanced.
- Constraint/index repair is shape-based for portability and reruns.

6.5 Application enforcement
---------------------------

- Provider-scoped mapping lookup.
- Exact organization/provider validation.
- Domain normalization/validation.
- DNS challenge and verification endpoints.
- Verified-domain gating for provisioning and OIDC/JIT.
- Claim conflicts, expiry, and audit events.
- Provider patch invalidates stale domain proof.
- OIDC respects provider ownership/domain state.

12. PHASE 5 - REAL INTEGRATION AND OPERATIONS ACCEPTANCE
===============================================================================

12.1 Real OIDC
--------------

12.2 SCIM with two providers
----------------------------

Verify provider A cannot see/change provider B; external IDs can repeat across
providers but not inside one provider; composite organization constraints reject
malformed rows; create/get/list/filter/put/patch/deactivate/reactivate; safe role
defaults; no admin escalation; token rotation/revocation; quarantine reporting and
manual rebind; document SCIM remove limitation.

12.3 Email
----------

Verify real receipt of invitation, verification, and reset; expiry/reuse; correct
from domain and SPF/DKIM/DMARC as applicable; exact HTTPS links; no enumeration;
retry/outbox behavior; alerting on delivery failure.

12.4 Object storage
-------------------

Verify upload/download/delete, size/type controls, organization boundary, access
from either replica, backup mirroring, deletion policy, versioning/lifecycle, no
public access, and least-privilege bucket credentials.

12.5 Stripe sandbox if in scope
-------------------------------

Verify checkout, test price/currency, signature, duplicate idempotency,
subscription/period transitions, failure/cancel states, seat/AI limits, portal,
cancellation/downgrade, and that no live key/price appears in staging.

12.6 Multi-replica/load
-----------------------

Verify both replicas receive traffic; sessions/rate limits/replay protection work
across replicas; migration does not race; uploads are shared; background work is
not duplicated. Run sustained load and record p50/p95/p99, errors, CPU, memory,
DB pool/connections, and Redis latency. Exercise graceful restart/replica loss.

12.7 Backup/restore/rollback
----------------------------

- Run backup and pg_restore --list.
- Copy off primary storage.
- Restore into a separately named disposable DB with verify_restore.sh and exact
  safety confirmation.
- Restore matching object versions into a fresh bucket.
- Check document/attachment references.
- Record RPO/RTO and evidence.
- Redeploy previous approved image in staging and verify health, login, projects,
  audit, SSO settings, and uploads.

Never restore over active staging automatically.

12.8 Monitoring/incident
------------------------

Configure and test alerts for HTTPS/readiness, restarts, sustained 5xx, Postgres/
Redis outage/pressure, migration failure, backup/object-backup failure, AI errors,
auth/reset/SSO spikes, and disk pressure. Prove a named human receives alerts.

12.9 External security
----------------------

With authorization, run exact-SHA ZAP/Schemathesis/security gates and an
independent penetration test focused on auth, tenancy, OIDC, SCIM, uploads, SSRF,
webhooks, rate limits, and privilege transitions. Fix/retest blockers and record
accepted risks.

- Real OIDC and two-provider SCIM pass.
- SMTP and S3/backup pass.
- Stripe sandbox passes if in scope.
- Sustained multi-replica test passes agreed targets.
- Restore/rollback pass.
- Alerts reach a named human.
- External security blockers close.
- Evidence maps to exact SHA/image digests.
